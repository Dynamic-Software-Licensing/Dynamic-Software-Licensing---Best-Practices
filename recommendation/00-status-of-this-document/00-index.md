# 00. Status of this Document

## Chapter Status

- Status: Working Draft
- Editorial maturity: outline
- Normative readiness: not started
- Open drafting points: yes

## Purpose

This chapter defines the status, intended role, maturity, and interpretation of the Dynamic Software Licensing recommendation.

It explains what this document is, what it is intended to achieve, and how it should be understood during the drafting phase and in later publication stages.

## Initiative Context

This document is part of **Dynamic Software Licensing (DSL)**, an **IABM initiative** focused on modern software licensing approaches for broadcast and media workflows.

The recommendation is being developed as a structured industry document that supports collaboration across manufacturers, broadcasters, media organizations, system integrators, and other stakeholders.

## Document Type

This document is an **industry recommendation**.

It is not currently a formal standard, certification framework, or legal specification. However, it is intentionally organized in a standard-like way to improve clarity, consistency, interoperability, and implementation guidance.

## Intended Role of the Recommendation

The recommendation is intended to:
- establish a common industry vocabulary,
- define a shared conceptual and architectural model,
- describe a practical target model for licensing, metering, trust, and policy handling,
- support migration away from fragmented or legacy licensing approaches,
- provide a basis for future alignment across the industry.

## Current Maturity

Current maturity: **Working Draft**

At this stage, this means:
- the document structure is being established,
- chapter boundaries are being defined,
- terminology is still being aligned,
- requirement language is still provisional,
- some chapters may still contain placeholders or editorial guidance.

## Unified Status Model

This recommendation uses a unified status model defined in `GOVERNANCE.md`.

The model has two layers:
- repository-level maturity,
- chapter-level status.

### Repository-Level Maturity

The repository-level maturity states are:
- Working Draft,
- Reviewed Draft,
- Candidate Recommendation,
- Published Recommendation.

### Chapter-Level Status

Each chapter should include a compact status block in its `00-index.md` file.

The block should use the following fields:
- `Status`,
- `Editorial maturity`,
- `Normative readiness`,
- `Open drafting points`.

The allowed values for these fields are defined in `GOVERNANCE.md` and should be used without local variants.

### Chapter Status Template

## How This Draft Should Be Interpreted

This draft should currently be interpreted as:
- an editorial working basis,
- a structured collaboration framework,
- a repository-level draft rather than a publication-ready recommendation.

Unless explicitly stated otherwise, examples, implementation references, and platform-specific content should not be interpreted as mandatory requirements.

## Versioning Approach

The recommendation is expected to evolve through versioned revisions.

A version may include:
- structural changes,
- chapter refinements,
- terminology updates,
- clarified requirement language,
- additional annex content,
- reclassification of content between normative and informative sections.

Significant changes should be reflected in:
- this chapter,
- `CHANGELOG.md`,
- the affected chapter or annex files.

## Normative Development Status

Normative keywords such as **MUST**, **SHOULD**, and **MAY** may appear in later drafting stages where appropriate.

At the current stage, the main objective is not yet to finalize all requirements, but to establish:
- a stable overall structure,
- consistent terminology,
- clear editorial intent,
- a reliable distinction between normative and informative content.

## Publication Intent

A later version of this document may be published as a formal recommendation of the Dynamic Software Licensing initiative.

Before that stage, the repository should reach a level of maturity that includes:
- structural completeness,
- terminology consistency,
- stable chapter ownership,
- reviewed requirement language,
- coherent annex structure,
- clear interpretation guidance.
